# Spec: 16KB page-size alignment, iOS packaging checks, transitive-dependency installation check, Expo Go per-package support

Status: **Implemented** (2026-09-18) — all four items shipped, in the phased order below. See
`.claude/rules/roadmap.md`'s Phase 4 entry for the shipped-file summary and `git log` for the
actual commits.
Author: assistant (with amit13091992@gmail.com)
Date: 2026-09-17 (spec) / 2026-09-18 (implementation complete)

## Summary

Four independent additions, each following the existing `detector → analyzer → data → command`
layering (see [architecture.md](../../.claude/rules/architecture.md)):

1. **Android 16KB page-size readiness** — detect `.so` libraries shipped by native
   dependencies and verify their ELF program-header alignment is 16KB-safe.
2. **iOS packaging parity checks** — a smaller, best-effort equivalent: dSYM presence and a
   couple of other IPA/build-artifact signals worth surfacing alongside the Android check.
3. **Transitive dependency completeness check** — for an installed package, verify its own
   `dependencies`/`peerDependencies` are actually present (declared or resolved), and suggest
   versions to install for anything missing.
4. **Expo Go per-package support** — a curated data set (same shape as
   `data/newArchitecture.ts`) answering "does this installed package work in Expo Go, or does
   it need a custom dev client?".

Each is scoped so it can ship independently; there's no ordering dependency between them.

## 1. Android 16KB page-size detection

> **Implemented as planned.** `utils/elf.ts`, `detectors/pageSize.ts`, `analyzers/pageSize.ts`,
> wired into `doctor` (not `check` — matches the plan). One naming difference from the draft
> types below: the shipped `PageSizeCheckResult.libraries` entries are typed as
> `NativeLibraryAlignment` (`src/types/pageSize.ts`), not `ElfAlignmentResult` — same shape,
> renamed for clarity during implementation. Test fixtures are hand-built minimal ELF64
> binaries generated by `scripts/generate-elf-fixtures.mjs`, exactly as scoped.

### Why this matters

Android 15+ devices can run with a 16KB memory page size (vs. the historical 4KB). A `.so`
shipped with `LOAD` segments aligned to 4KB will fail to load — this is a real, current
compatibility class (Google started enforcing 16KB-aligned uploads for some Play Store tracks
in 2025). This is a natural `doctor`-style check: static, deterministic, no execution of
untrusted code (satisfies [security.md](../../.claude/rules/security.md) — this is pure binary
parsing, not execution).

### What we detect

For every native dependency that ships a prebuilt `.so` (found under `node_modules/**/*.so`,
typically inside an AAR extracted at `android/**/jni/<abi>/*.so` or a package's
`android/src/main/jniLibs/<abi>/*.so`), parse the ELF program header table and check whether
every `PT_LOAD` segment's `p_align` is `>= 0x4000` (16384).

This requires an ELF parser reading:
- ELF header (`e_phoff`, `e_phnum`, `e_phentsize`, class = 32/64-bit via `EI_CLASS`)
- Program header table entries where `p_type == PT_LOAD`, reading `p_align`

No existing dependency in this repo does ELF parsing — this is binary structure parsing off a
fixed-size, well-documented format (~150 lines), not worth pulling in a third-party parser for
(see [dependency-policy.md](../../.claude/rules/dependency-policy.md) — `packages/core`-equivalent
minimalism applies to this single-package repo too). Read as a `Buffer` via `fs.readFileSync`;
never execute the binary.

### New files

- `src/types/pageSize.ts`
  ```ts
  export interface ElfAlignmentResult {
    path: string;        // relative path to the .so
    abi: string;          // arm64-v8a, armeabi-v7a, x86, x86_64
    is16kAligned: boolean;
    maxLoadAlign: number; // largest p_align seen across PT_LOAD segments, for diagnostics
  }

  export interface PageSizeCheckResult {
    package: string;
    version: string;
    libraries: ElfAlignmentResult[];
    status: 'aligned' | 'unaligned' | 'not-checked'; // not-checked: no .so found for this package
  }
  ```
- `src/utils/elf.ts` — `parseElfAlignment(buffer: Buffer): { maxLoadAlign: number } | null`
  (returns `null` for a non-ELF or unparseable file rather than throwing — untrusted repo
  content, per [security.md](../../.claude/rules/security.md)).
- `src/detectors/pageSize.ts` — `findNativeLibraries(cwd, dependencies): Map<packageName, soFilePaths[]>`,
  walking each dependency's install directory (bounded depth, skip symlinks) for `*.so` under
  a `jniLibs/` or `jni/` path segment, grouped by ABI directory name.
- `src/analyzers/pageSize.ts` — `analyzePageSize(cwd, dependencies): PageSizeCheckResult[]`,
  combining the detector + `parseElfAlignment`, arm64-v8a and x86_64 only (16KB pages are an
  arm64/x86_64 concern; 32-bit ABIs are unaffected and should report `not-checked` rather than
  a false failure).

### Wiring

- `doctor` gains a new section, human + `--json` (`pageSize` field), following the same
  `EnvironmentRequirement`-adjacent shape as the existing Android/iOS sections — but this one
  is per-package, not a single environment value, so it's closer to `NewArchCheckResult[]` in
  shape (array under a `pageSize16k` key) than to `EnvironmentRequirement`.
- Verdict contribution: any `unaligned` result contributes a `warning`-level entry (not
  `error`) into `verdictFromRequirements`/`combineVerdicts` — this is a forward-looking
  readiness signal, not something that breaks today's builds.

### Testing

Fixture `.so` files (hand-built minimal ELF binaries, a handful of bytes each — no real
compiled library needed) under `test-fixtures/elf/{aligned,unaligned}.so`, generated once by a
small script and checked in. Unit tests: `elf.test.ts` (parser correctness against both
fixtures + a malformed/truncated buffer + a non-ELF file), `pageSize.test.ts` (detector +
analyzer, using a fixture project structure).

### Limitations to call out in the doc

- Only checks prebuilt binaries already present in `node_modules` (post-`npm install`) — a
  package that compiles from source at build time (most RN autolinked modules with a
  `CMakeLists.txt`/NDK build) won't have a `.so` to inspect until the Android build runs; this
  check has partial coverage by design, not a bug.
- No attempt to *fix* alignment (e.g. re-running `zipalign`) — detection only, matching this
  package's read-only philosophy.

## 2. iOS packaging parity checks

> **Implemented at reduced scope, as the spec anticipated.** Only the dSYM-presence check
> shipped (`utils/zip.ts`, `detectors/ios/ipaPackage.ts`, `analyzers/iosPackage.ts`), via
> `doctor --ipa <path>`. Bitcode markers and unsigned-framework checks were **not built** —
> left deferred pending confirmation they're actually wanted, per the "confidence note" below.
> The result type shipped as `IosPackageCheckResult { appName, hasDsym, notes }`, simpler than
> the draft `{ hasDsym, missingDsymTargets, bitcodePresent, notes }` shape since only the
> single-app dSYM check exists so far — `missingDsymTargets`/`bitcodePresent` can be added
> back if/when embedded-framework dSYMs and bitcode detection are built.

### Framing

16KB page size is **not an iOS problem** — iOS devices have used 16KB pages on arm64 hardware
for years already, so there's no iOS equivalent of the Android check above. What the user is
pointing at is a different, smaller class of "does this IPA look properly built" signals worth
surfacing next to the Android section for parity. Ship this as a lighter-weight, best-effort
check — a nit-tier addition, not full IPA validation.

### What we detect (all static, no simulator/device execution)

Given a path to a built `.ipa` (or an `.xcarchive` if that's what's available — accept either
via `--ipa <path>` on `doctor`, since neither exists in a fresh checkout and this can't be
inferred from `cwd` the way the rest of `doctor` works):

1. **dSYM presence** — unzip (read-only, in-memory) and check whether
   `<App>.app.dSYM/Contents/Resources/DWARF/<AppName>` exists for the main binary and for any
   embedded frameworks. Missing dSYMs mean unsymbolicated crash reports.
2. **Bitcode markers** (informational only) — flag if a `__LLVM` segment is still present;
   Xcode 14+ dropped bitcode, so its presence usually means a stale build config, not itself
   an error.
3. **Embedded `.so`/non-Apple-signed dynamic libraries** — sanity check that nothing
   unexpected snuck into `Frameworks/` unsigned.

### New files

- `src/types/iosPackage.ts` — `IosPackageCheckResult { hasDsym: boolean; missingDsymTargets: string[]; bitcodePresent: boolean; notes: string[] }`
- `src/detectors/ios/ipaPackage.ts` — reads the `.ipa` (a zip) via Node's built-in
  `node:zlib`/a minimal zip central-directory reader (same "don't add a dependency for this"
  reasoning as the ELF parser — IPA is a plain zip, and we only need the central directory
  listing + a couple of file reads, not full extraction).
- `src/analyzers/iosPackage.ts` — turns the detector's raw listing into `IosPackageCheckResult`.

### Wiring

- New optional flag on `doctor`: `--ipa <path>`. When absent, this section is simply omitted
  from output (not an error) — this is opt-in because, unlike every other `doctor` check, it
  needs an artifact that doesn't exist until after a build, so it can't run as part of the
  default zero-config `doctor` pass.

### Confidence note (flagging per the user's own "not pretty sure")

This is the least-specified of the four asks. Treat dSYM-presence as the one concrete,
well-understood check; bitcode/unsigned-framework checks are secondary and should be built
second, after confirming with the user (or real IPA fixtures) that they're actually wanted —
don't over-build speculative checks here per
[performance.md](../../.claude/rules/performance.md)/[code-style.md](../../.claude/rules/code-style.md)
("don't implement functionality a phase doesn't require").

### Testing

A tiny hand-built zip fixture (`test-fixtures/ipa/with-dsym.ipa`, `without-dsym.ipa`) — a few
KB each, built by a `scripts/` generator script, not committed as opaque binaries without a
way to regenerate them.

## 3. Transitive dependency completeness check

> **Implemented as planned**, wired into `check` (not `doctor`) as specced.
> `detectors/dependencyCompleteness.ts`, `analyzers/dependencyCompleteness.ts`. The human
> output additionally prints a package-manager-aware install command per gap (`npm
> install`/`yarn add`/`pnpm add`/`bun add`, matching whatever `utils/lockfile.ts` detected) —
> the plan's "suggested install commands" is realized as an `installCommand()` helper in
> `commands/check.ts` rather than inside the analyzer, keeping the analyzer free of any
> presentation concerns.

### What's actually being asked

For each installed top-level dependency, look at *its* `dependencies` (and `peerDependencies`)
as declared in *its own* `package.json` inside `node_modules/<pkg>/package.json`, and verify
each of those is actually resolvable in this project (present in `node_modules`, or in the
lockfile). Where one is missing, report the name and the version range the parent package
wants, so the user knows what to `npm install`.

This is distinct from existing dependency-graph code:
- `utils/dependencyGraph.ts` already builds a full transitive graph for npm from
  `package-lock.json`'s `packages` structure — a *missing* dependency won't appear there at
  all (npm's own install would normally have failed), so this check is really aimed at the
  **yarn/pnpm/bun** case (`hierarchyComplete: false` today per
  [known-limitations.md](../../.claude/rules/known-limitations.md)) and at **peerDependencies**,
  which npm/yarn/pnpm all handle differently (auto-install vs. warn vs. strict) and which a
  lockfile-only view doesn't surface uniformly.
- It's also useful as a **project-agnostic-of-lockfile** sanity check: `node_modules` can drift
  from the lockfile (partial installs, manual `npm link`, CI cache staleness) — reading actual
  `node_modules/<pkg>/package.json` catches that drift a lockfile-only check can't.

### Algorithm

For each direct dependency `pkg` in the project:
1. Read `node_modules/<pkg>/package.json` (skip if missing — that's a separate, existing
   "installed vs. declared" gap, not this check's job).
2. For each entry in its `dependencies` and `peerDependencies`:
   - Resolve: does `node_modules/<dep>/package.json` (or, for scoped hoisting,
     `node_modules/<pkg>/node_modules/<dep>/package.json`) exist?
   - If yes: does its installed `version` satisfy the requested range (`semver.satisfies`,
     reusing `utils/versionComparison.ts`)?
   - If missing or unsatisfied: record `{ parent: pkg, dependency: dep, requiredRange, installedVersion: string | null, kind: 'dependency' | 'peerDependency' }`.
3. `peerDependencies` marked `peerDependenciesMeta.<name>.optional: true` are reported at
   `info` severity, not `warning` — an absent optional peer is normal, not a gap.

### New files

- `src/types/dependencyCompleteness.ts`
  ```ts
  export interface MissingDependency {
    parent: string;
    parentVersion: string;
    dependency: string;
    requiredRange: string;
    installedVersion: string | null; // null = not installed at all; string = installed but out of range
    kind: 'dependency' | 'peerDependency';
    optional: boolean;
  }
  ```
- `src/detectors/dependencyCompleteness.ts` — `readInstalledDependencyManifest(cwd, pkg): { dependencies, peerDependencies, peerDependenciesMeta, version } | null`
- `src/analyzers/dependencyCompleteness.ts` — `analyzeDependencyCompleteness(cwd, dependencies: DependencyInfo[]): MissingDependency[]`

### Wiring

- New section in `check` (not `doctor` — this is a dependency-graph concern, same family as
  `why`/`tree`, not an environment/toolchain concern). Human output: a
  "Missing/Unsatisfied Sub-dependencies" section listing each gap with the suggested install
  command (`npm install <dependency>@<requiredRange>` — respect whichever manager
  `utils/lockfile.ts` already detected for this project, not hardcoded to npm). `--json`:
  new `dependencyCompleteness: MissingDependency[]` field.
- Uncertainty handling per [ADR-0004](../../.claude/rules/code-style.md#uncertainty): if a
  package's own `package.json` can't be read (corrupted, unusual layout), report it as a
  distinct `not-checked` entry rather than silently skipping — don't let an unreadable
  manifest look identical to "everything's fine."

### Testing

Fixture project under `test-fixtures/` with a `node_modules/parent-pkg` whose own
`package.json` declares a dependency that's deliberately absent from the fixture's
`node_modules`, plus one that's present but at a version outside the requested range, plus one
satisfied peer marked optional. Covers all three branches (missing / unsatisfied / optional-skip).

## 4. Expo Go per-package support

> **Implemented as planned.** `data/expo/goSupport.ts`, `analyzers/expoGoSupport.ts`, wired
> into `check` alongside the existing New Architecture section, exactly as specced — same
> curated-entry-with-native-module-pattern-fallback shape as `analyzers/newArchitecture.ts`,
> and the `expoGoSupport` `--json` key is present only when `isExpoProject` is true.

### What's actually being asked

Distinct from the *existing* Expo work (`data/expo/registry.ts` /
`analyzers/expoCompatibility.ts`), which maps **Expo SDK version → expected React Native
version**. This ask is per-*package*: for each installed dependency, is it usable inside the
**Expo Go** sandbox app, or does it require native code Expo Go doesn't ship (meaning the
project needs a custom dev client / bare workflow)?

### Data shape (mirrors `data/newArchitecture.ts` exactly — same pattern, same team already
knows how to maintain it)

- `src/types/expoGo.ts`
  ```ts
  export type ExpoGoSupport = 'supported' | 'unsupported' | 'unknown';

  export interface ExpoGoPackageInfo {
    package: string;
    support: ExpoGoSupport;
    reason?: string;   // e.g. "requires custom native code not in Expo Go"
    notes?: string;
  }

  export interface ExpoGoCheckResult {
    package: string;
    version: string;
    support: ExpoGoSupport;
    reason?: string;
  }
  ```
- `src/data/expo/goSupport.ts` — curated list, seeded from Expo's own published "Unsupported in
  Expo Go" package list (e.g. most `react-native-*` community native modules, anything not in
  the `expo-*` namespace or the small allowlisted set Expo Go bundles) plus explicit entries
  for the common ones (`react-native-reanimated` — supported since it's bundled;
  `react-native-vision-camera` — unsupported, needs custom native code; etc.). Same staleness
  caveat as `data/newArchitecture.ts` / `data/expo/registry.ts` — document it identically and
  point at `MAINTENANCE.md`-style guidance for future updates.
- `src/analyzers/expoGoSupport.ts` — `analyzeExpoGoSupport(dependencies, isExpoProject): ExpoGoCheckResult[]`.
  Only runs (returns non-empty) when `detectExpo()` says this *is* an Expo project — for a bare
  RN project, "supported in Expo Go" isn't a meaningful question, so short-circuit to `[]`
  rather than emitting confusing noise.

  Heuristic for packages with no curated entry (same shape as `LIKELY_NATIVE_MODULE_PATTERN` in
  `analyzers/newArchitecture.ts`): if the package name matches the native-module pattern and
  has no curated entry, report `support: 'unknown'` with a note to verify manually — never
  default an unknown package to `'supported'` (this would hide a real incompatibility, which is
  exactly what [code-style.md](../../.claude/rules/code-style.md)'s ADR-0004 rules out).

### Wiring

- Extends `check` output (not `doctor`) alongside the existing `newArchitecture` section, since
  it's the same "per-installed-package compatibility flag" shape and both only matter once
  New-Architecture-style native-module scanning is already happening. `--json`: new
  `expoGoSupport: ExpoGoCheckResult[]` field, present (possibly empty) only when
  `isExpoProject` is true — omit the key entirely for non-Expo projects rather than emitting an
  empty array, so consumers can branch on key presence.

### Testing

`expoGoSupport.test.ts`: curated-entry lookup, unknown-native-module fallback, tooling-package
exclusion (reuse `TOOLING_EXCLUSION_PATTERN`-equivalent), and the short-circuit for non-Expo
projects.

## Implementation plan / phasing

Shipped independently, in this order (cheapest + most self-contained first, riskiest last) —
all four landed on 2026-09-18:

| Order | Feature | Why this order | Status |
|---|---|---|---|
| 1 | Expo Go per-package support (#4) | Pure data + analyzer, identical pattern to `newArchitecture.ts` already in the codebase — lowest risk, fastest to review. | ✅ Shipped |
| 2 | Transitive dependency completeness (#3) | Filesystem + semver only, no new binary parsing; reuses `versionComparison.ts`/`lockfile.ts`. | ✅ Shipped |
| 3 | Android 16KB page-size detection (#1) | New binary-parsing surface (`utils/elf.ts`) — needs its own fixture-generation step and careful malformed-input handling per [security.md](../../.claude/rules/security.md), but self-contained and high-value (real, current Play Store enforcement). | ✅ Shipped |
| 4 | iOS packaging parity checks (#2) | Least specified, opt-in via `--ipa` flag, needs a follow-up conversation to confirm which checks beyond dSYM presence are actually wanted before building past the first one. | ✅ Shipped, dSYM-presence only (bitcode/unsigned-framework checks intentionally deferred) |

For each: implementation → unit tests → wire into the relevant command's human + `--json`
output → update `roadmap.md`'s Recent Changes / Next Steps once shipped, per
[documentation.md](../../.claude/rules/documentation.md). None of these touch
authentication/authorization/secrets/sandboxing/external-tool-execution, so the
[security.md](../../.claude/rules/security.md) enhanced review path doesn't apply — normal
`code-reviewer` + `architecture-reviewer` agent review is sufficient, except item #1/#2 (ELF
and zip parsing of untrusted repo/build content) should still get a deliberate pass for
malformed-input handling (fuzz a few truncated/corrupt fixtures) even though it's not
"security review" in the AuthN/AuthZ sense.

No new third-party dependencies needed for any of the four (ELF and zip-central-directory
parsing are both small, fixed-format, and avoidable-dependency territory per
[dependency-policy.md](../../.claude/rules/dependency-policy.md)) — confirmed true as shipped;
`package.json` gained no new runtime dependencies for this work.

## Post-implementation follow-ups (not yet built)

- iOS: embedded-framework dSYMs (each `.framework` under `Frameworks/` can have its own dSYM,
  not just the main app) and the bitcode-marker check from the original spec.
- Android: no attempt to *fix* alignment (e.g. re-running `zipalign`) — detection only, by
  design.
- Both new binary parsers (`utils/elf.ts`, `utils/zip.ts`) have unit coverage for
  malformed/truncated/non-matching input via hand-built fixtures, but neither has been
  exercised against a real compiled `.so` or a real Xcode-produced `.ipa` — worth doing before
  leaning on this for a real release-readiness gate.
